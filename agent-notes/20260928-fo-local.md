# 2026-09-28 /fo/ 本地边界判断

Case: `psa-cf-5s-shield-20260815`. web-case 仍是 `patching`。没有 `serverAccepted`。本笔记只读桥与 `bridge-src.jsonl` 末两轮，不改 runner、不开新 trace、不提交网络。

## 1. 已证明的宿主事实

- **KP 镜像有效，且不是 `window.KP`**：末两轮 `errors=[]`；探针 `kp=undefined`、`kpOwn=false`；`xdi` 与 `xdiWin` 都是 `function`；Turnstile `onloadN=2`。编排前置原型桥把方法落到 Window，页面不再因 `KP.call` 抛错。没有定义 `window.KP`，没有改 orchestrate 字节码。
- **`/fo/` 已由页面 XHR 自己发出**：末两轮 `counts.fo=3`，`eb=0`，`jsd=0`，`orchestrate=1`。三次都是 `kind=xhr` `POST`，路径模板 `/cdn-cgi/challenge-platform/h/b/fo/{id}:{id}:{id}/{id}/{id}`。`hdr` 名只有 `cf-chl`、`cf-chl-ra`。`bodyBytes=2306`，`served=false`。两轮 sha256 互不一致（见 `20260928-ruyidom-bridge.md`），body 含动态字段。
- **资源 handler 对 `/fo/` 返回 `null`**：只映射 orchestrate GET、Turnstile api.js（第二次起）、文档 path；其余走 `blockUnmapped`，计入 `blocked`。取消通道来自 `http-on-modify-request` 的 necko `cancel`，目的是离线进程活到打印摘要，**不是解题响应**。
- **只作观察的计数器**（`beforeParse` 页面隔间包装，native-like `toString`）：Worker `__wk`、iframe `__ifr`/`__ifrX`、blob `__blob`、`randomUUID` `__uuid`、`getEntries` `__ent`、`RTCPeerConnection`/`createOffer`/`ice`、message/`honk`、`onloadN`。它们证明「调用发生过 / 未发生过」，本身不是已补的解题面。
- **末两轮探针一致**：`wk=1`，`ifr=1`，`ifrX=0`，`pc=1`，`ice=0`，`offer=1/0/0`，`msg=0`，`honk=0`，`uuid=1`，`ent=1`，`blob=1`，`optKeys=36`，`turnstile=object`，`turnstileTags=2`。
- **时间顺序（jsonl）**：script 映射（Turnstile 惰性 → orchestrate served → Turnstile served → favicon/blocked → 再 Turnstile）之后，才出现三组 `hdr(POST cf-chl*)` + `wire(/fo/ served=false)`；再之后才是 necko 取消的无关 GET。因此 **`/fo/` 发出发生在摘要探针之前，且不依赖 createOffer settle**。

不要把更早「无页面隔间探针、fo=0、只有 KP.call」的历史轮次当成当前事实。

## 2. 下一刀：单一外部宿主面与可证伪假说

下一刀只能动一个外部宿主面（`external-host-only`）。不改 VM/opcode，不造 `window.KP`，不把异会话 `/fo/` 响应体硬编码进仓库。`-AllowNetwork` 不是禁令，只是这轮启动器没开。

### 主假说 H1（优先）

页面停在 **「`/fo/` 没有本地响应」**：XHR 已 send，handler 回 `null`，通道被 necko 取消，页面拿不到可读的 status/body，挑战链无法像有头材料那样继续（有头复看是多次 `/fo/` POST 200 后才出现 clearance 名）。

**证伪方式**：在不联网、不写死历史 body 的前提下，为 `/fo/` 提供**来自当次材料/捕获形状的本地应答**（或等价的受控 stub：固定 status + 空/最小 body 且可观测页面是否继续）。若页面在收到本地应答后继续发下一跳（更多 `/fo/`、或其它 challenge-platform 路径、或探针状态相对末两轮发生变化），则 H1 成立方向确认；若应答后 wire/探针完全不变，则 H1 被削弱，转看 H2。

### 并行观察假说 H2（次级，不能解释「发不出 /fo/」）

页面另有缺口在 **`createOffer` 不 settle / Worker 无 honk / iframe 指纹面**：`offer=1/0/0` 表示调用 1 次、15s pump 内既未 `__offerS` 也未 `__offerF`（仍 pending）；`honk=0`，`ice=0`。

**与 H1 的时间关系**：`/fo/` 三次 POST 已经出现在 wire 上，因此 **createOffer 未 settle 不是「发不出 `/fo/`」的原因**。它仍可能是响应之后、或与 `/fo/` 并行的指纹缺口；只有在 H1 被证伪（本地 `/fo/` 应答后链仍停）时，才把下一刀改到 WebRTC/Worker/iframe 这一个面上。

## 3. 证据不够区分时缺的观测

当前 **不能** 仅凭末两轮在 H1/H2 之间做完因排除，缺：

1. **页面是否读取了 `/fo/` 响应**：XHR `readyState` / `status` / `responseText` 长度（或 fetch 等价），在 send 之后、pump 结束之前。现在只有「发出 + served=false + necko cancel」，没有「页面侧读到了什么」。
2. **`createOffer` promise 终态**：已有 `1/0/0` ⇒ 在 15s 内既非 fulfilled 也非 rejected（pending）。仍缺：更长 pump 或显式 `finally` 标记后是否永远 pending，以及 iframe `contentWindow` 上的 offer 是否与顶层同一计数。

不要发明新 API；上述两项用现有页面隔间探针扩展计数即可，仍保持一次只动一个外部面。

## 4. 边界重申

- 取消通道 ≠ 解题响应。
- `served=false` 的 `/fo/` ≠ `serverAccepted`。
- 观察计数器上涨 ≠ 已补齐该 API 的浏览器语义。
